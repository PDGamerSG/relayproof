# Configuration

Every setting RelayProof reads, its default, and the file that reads it. There is no `.env.example` in the repository, and no program here loads a `.env` file of its own. The hosted container takes its settings from the environment Render sets, the demo scripts take theirs from the shell, and the site takes its two variables from the shell or from Vite's environment files. Git ignores `.env` and `.env.*` (`.gitignore:8-10`, `bifrost-shadow/site/.gitignore:2`).

## How settings are loaded

The hosted backend reads its settings in four layers. Each layer can override the one before it.

1. Render sets the variables listed in `render.yaml` (`render.yaml:25-43`). `ANTHROPIC_API_KEY` has no value in the file and is entered in the Render dashboard (`render.yaml:30-33`).
2. The image sets `PORT=10000` and `WORK_DIR=/home/demo/gateway` (`bifrost-shadow/deploy/Dockerfile:33`).
3. `entrypoint.sh` picks a mode, fills claude-mode defaults for anything still unset, and exports them (`bifrost-shadow/deploy/entrypoint.sh:24-63`). It copies one of two gateway configs to `$WORK_DIR/config.json` (`bifrost-shadow/deploy/entrypoint.sh:33`, `bifrost-shadow/deploy/entrypoint.sh:55`) and passes some values to the programs as flags (`bifrost-shadow/deploy/entrypoint.sh:66-70`).
4. Each program reads its own environment. The front door uses a flag if one is given, then the variable, then its built-in default (`bifrost-shadow/examples/shadow-demo/frontdoor/main.go:83-111`). A duration can be a Go duration such as `15s` or a plain number of seconds; a value it cannot read is logged and replaced by the default (`bifrost-shadow/examples/shadow-demo/frontdoor/main.go:160-173`). A number that is negative or not a number also falls back to the default (`bifrost-shadow/examples/shadow-demo/frontdoor/main.go:153-158`).

The gateway reads `config.json` from its app directory. The Claude config names its provider key as `env.ANTHROPIC_API_KEY`, so the key comes from the environment and never sits in the file (`bifrost-shadow/deploy/gateway-claude.json:13`). The fault proxy and the mock upstream read flags only.

The site has two variables. `vite.config.ts` reads `SHADOW_BACKEND` from the shell when the dev server starts (`bifrost-shadow/site/vite.config.ts:9`). Browser code reads `VITE_SHADOW_API` through `import.meta.env` (`bifrost-shadow/site/src/live/backend.ts:16`), so its value is public in the built site.

Sources: `render.yaml`, `bifrost-shadow/deploy/Dockerfile`, `bifrost-shadow/deploy/entrypoint.sh`, `bifrost-shadow/deploy/gateway-claude.json`, `bifrost-shadow/examples/shadow-demo/frontdoor/main.go`, `bifrost-shadow/site/vite.config.ts`, `bifrost-shadow/site/src/live/backend.ts`.

## Shadow plugin configuration

The plugin reads the `config` object of the `shadow` entry in the gateway's `plugins` list. The table gives each main field's default from `bifrost-shadow/plugins/shadow/config.go` and its value in the two deploy configs. In the two deploy-config columns, a bare `:line` refers to the file named in the column heading. The full field reference, including every threshold and canary option, is in [shadow-traffic.mdx](../bifrost-shadow/docs/features/shadow-traffic.mdx#field-reference).

A minimal block for your own gateway's `config.json`, from `bifrost-shadow/README.md`. It mirrors 10% of `gpt-4o` traffic to `gpt-4o-mini`, judges each pair with `gpt-4o`, caps evaluation spend at $20 a day and turns on the canary guard:

```json
{
  "plugins": [{
    "enabled": true,
    "name": "shadow",
    "config": {
      "sample_rate": 0.1,
      "experiments": [{
        "source": { "provider": "openai", "model": "gpt-4o" },
        "candidates": [{ "provider": "openai", "model": "gpt-4o-mini" }]
      }],
      "judge": { "provider": "openai", "model": "gpt-4o" },
      "daily_budget_usd": 20,
      "persist_path": "shadow.jsonl",
      "canary": { "auto_rollback": true }
    }
  }]
}
```

The console's Set up tab builds the same block from a form and checks it against the plugin's rules (`bifrost-shadow/site/src/live/Setup.tsx`).
